# GPU 异步帧传输与着色器合成实现报告

日期：2026-10-28。Windows 11、RTX 3060 Laptop GPU、Temurin JDK 21。参考 `rehan-remade/universal-modder` 中 `examples/minecraft-gta5-passthrough`（MIT 许可）的帧导出与 `MCPassthrough.fx` 重投影思路，按 Minecraft 1.21.1 的原生 OpenGL 重写，没有复制参考代码。

## 实现了什么

替换了原来的整条画面路径：后台 `glReadPixels` 同步读回 → 文件锁 → 主端再同步读回本地颜色和深度 → Java 逐像素比较或正向投影 → `glTexSubImage2D` 写回。

- **后台异步导出（`FrameExporter`）**：世界层画完、手部画之前，把颜色和深度读进同一个 PBO，然后插入 `glFenceSync`；3 个 PBO 轮转使用。下一次调用时检查栅栏，完成的才映射并发布，渲染线程不会等待 GPU。一个 PBO 超过 1 秒没完成就放弃。去掉了原来约 30 FPS 的采集限速。
- **帧文件 seqlock（`FrameFile`）**：每个槽位头部有一个序号，写入期间为奇数。读者只接受"复制前为偶数、复制后没变"的帧；写者不加锁，也从不等待。取代了跨进程文件锁（以前读到忙槽位只能放弃这一帧）。
- **帧携带实际渲染姿态**：后台发布的 `Pose` 取自本帧真实的 `Camera` 位置、旋转和 `RenderSystem.getProjectionMatrix()`，不再沿用主端请求的姿态。
- **主端 GPU 合成（`RemoteCompositor`）**：远端颜色上传为 `RGBA8` 纹理，深度上传为 `R32F` 纹理，然后画一个全屏三角形。片元着色器写出远端表面在当前相机下的 `gl_FragDepth`，由硬件深度测试（`GL_LESS`）对比主端自己的深度缓冲。主端不读回任何像素，也不对正在绑定的深度纹理采样，没有反馈回路。
  - 当前相机和远端渲染姿态完全一致时，直接按像素采样。
  - 不一致时，每个像素沿当前视线做 40 个对数步长的步进，找到第一个"落在远端深度表面之后"的点，再二分 8 次细化。如果交点与远端表面重建位置相差超过 `0.08 + 0.02·t` 米，说明这是遮挡被揭开的区域，这个像素就丢弃，留给主端自己的画面，不把远端物体边缘拉成拖影。
  - 所有 GL 状态改动都经过 `GlStateManager`，结束后恢复，保证原版状态缓存一致。
- **过期隐藏**：远端帧龄超过 1 秒时不再绘制，避免冻结的远端画面一直留在屏幕上。
- **对照路径**：旧的 CPU 合成保留，用 `-Dmmlf.compositor=cpu` 开启。
- **后台玩家每帧同步**：后台在每帧准挑 `GameRenderer.pick` 之前，把玩家位置、上一帧位置和朝向都设为主端玩家的值，原生射线不再落后一个 tick 的插值。
- 统计日志：主端每秒输出 `render.composite/gpu_frames`（直接合成帧数、重投影帧数、帧龄）；后台输出 `render.capture/frame`（含 `readbackMs`）。

## 发现的问题与解决

1. `org.joml.*` 通配导入与 `java.lang.Math` 冲突，编译失败；改为显式导入 `Matrix4f` 和 `Quaternionf`。
2. 第一次 Fabric 主端运行中，转向自测发生在远端帧到达之前，所有采样都是 `reprojected=false`，重投影没有被测到。自测门槛改为"收到第一张远端帧"后，下一轮运行记录到重投影帧。
3. 自测脚本的坐标是按 Fabric 当主写死的。NeoForge 当主时，它测的是本地方块：碰撞 `shapes=0 passed=false`，交互目标归属 NeoForge 自己。自测改为根据场景中远端 `demo_block` 所在的一侧，对 x 坐标和朝向做镜像。
4. 本地玩家的视角朝向不插值：自测每 tick 改一次朝向，画面每秒 60 帧，所以大部分帧前后姿态相同、走直接合成。这是预期行为，不是 bug；鼠标连续转动时重投影帧的比例会更高。

## 得到了什么结果

自动化测试：

- `./gradlew.bat build`：全部模块编译成功，自动化测试通过。
- `common` 模块测试：`FrameFileTest` 3 项（新增"并发写者永远不会产生撕裂帧"：写线程持续覆盖 256×256 帧 1.5 秒，读者每次接受的帧颜色和深度都只来自同一帧）、`PixelCompositorTest` 2 项、`DepthReprojectionTest` 1 项，均通过。着色器的重投影算法没有单元测试，只经过实机运行。

真实 Minecraft：

- **Fabric 主端，客户端托管**（session-1955423682484589279）：日志 `COMPOSITE READY remote=neoforge mode=gpu`、`gpu_ready 1280x720`；跨端交互、反向事件、第三方活板门、中键选取、远端放置、破坏粒子、碰撞自测全部通过。截图 `fabric-primary-core.png`：橙色 NeoForge 方块和 NeoForge 活板门合成在 Fabric 窗口里，遮挡和边缘正确。`fabric-primary-item.png`：远端放置的活板门、原生手持模型和快捷栏图标都正常显示。后台读回从发起到可映射，中位数 13.4 ms、p90 16.2 ms（53 个采样）；合成时远端帧龄中位数 17.8 ms、p90 28.7 ms。
- **NeoForge 主端，客户端托管**（session-16136809274857667231，镜像修正之前）：`COMPOSITE READY remote=fabric mode=gpu`。转向过程中记录到 35 帧重投影合成（逐秒统计 2/5/6/9/13 帧），截图 `neoforge-primary-turning.png` 是转向中途的画面，远端蓝色 Fabric 方块位置正确，没有可见拖影或空洞。后台读回中位数 12.8 ms、p90 17.7 ms；帧龄大多在 11–41 ms。这一轮交互和碰撞自测结果因上述问题 3 不能采信。本轮在粒子自测结束约 1 秒后，主窗口正常关闭（`Stopping!` 后服务端保存退出，没有崩溃报告）。用户确认是手动关闭的窗口，不是程序异常。会话结束后没有残留的 MMLF Java 进程。
- **NeoForge 主端，客户端托管，镜像自测**（session-4973500186604494280）：`COMPOSITE READY remote=fabric mode=gpu`；相机控制通过；碰撞 `shapes=1 dx=-0.2 passed=true`；Fabric 侧日志 `INTERACTION runtime=fabric … mmlf_fabric_test:demo_block[lit=true]` 和 `… mcwdoors:oak_four_panel_door[… open=true …]`，说明远端测试方块和第三方门都在 Fabric 中原生执行。截图 `neoforge-primary-core.png`、`neoforge-primary-thirdparty.png`：远端蓝色方块和打开的 Fabric 门合成在 NeoForge 窗口中。共记录 79 帧重投影合成。后台读回中位数 12.9 ms、p90 17.3 ms；帧龄中位数 16.5 ms、p90 28.4 ms（40 个逐秒采样）。**没有覆盖**：这一方向的中键选取和远端放置。镜像后的射线先打到 NeoForge 自己的地面（Fabric 侧是薄的竖门，与 NeoForge 侧的贴地活板门不对称），所以选取和放置都在主端本地执行，不能算作远端物品路径通过。

本次没有做用户手动操作和主观流畅度验收。

## 限制与下一步

- 重投影只在自测的慢速转向下实机运行过，没有经过快速甩鼠标、高速飞行、第三人称的逐帧检查。参考项目所说的"调试视图"（深度条纹、深度差）还没实现。
- 远端的透明材质（水、玻璃）仍按不透明合成，背景是远端自己的天空颜色；主端的半透明表面会整体挡住它后面的远端物体。
- 主端仍通过 CPU 把帧从共享文件复制到直接缓冲区再上传纹理，1080p 下每帧约 16 MB。下一步可以改为 PBO 异步上传。
- 手部和图标仍走原有的 `VisualLayers` 同步读回通道，还没换成参考项目那种"手部/HUD 单独一层"的方式。
- 原生按键转发（由拥有目标的一端客户端自己执行点击）和屏障方块碰撞镜像还没实现。

## 用户实测后的修复（2026-10-28 晚）

用户报告：NeoForge 当主时，转动视角出现摩尔纹，天空的云会抽搐；中键选取远端物品时，物品栏先显示纸张；门在物品栏和手上的样子不对。

1. **摩尔纹**：把用户会话 session-3483548941092128379 的 `fabric.frames` 解码后发现，Fabric 当后台时的画面里包含完整的原版地面和方块选择框（覆盖率 75.9%）。原因是 Fabric API Indigo 用 `@Redirect` 接管了区块构建中的 `renderBatched`，原来挂在这个方法上的过滤对 Fabric 不起作用。远端地面和主端地面深度几乎相同，重投影时就会 z-fighting。改为新增 `SectionCompilerMixin`，在 `SectionCompiler.compile*` 循环里包装 `BlockState.getRenderShape()`，不属于本端的方块返回 `INVISIBLE`。第一版用 `method="compile"`，在 NeoForge 上只匹配到转发用的重载，注入失败，进入世界时崩溃；改成 `compile*` 后在两个加载器上都注入成功。session-3227772604184204266 实测：Fabric 后台帧的覆盖率降到 0.7%，只剩云。
2. **方块选择框**：后台不再绘制方块选择框（`HitOutlineMixin`）。NeoForge 后台帧里那个青色线框，就是半透明的选择框混入了背景色。
3. **云抽搐**：同一份帧里能看到，后台画的云写入了深度，因此也被合成到主端；两端的云按各自的游戏时间移动，位置对不上。改为后台连接后自动关闭云渲染。**已编译，尚未实机验证。**
4. **纸张闪现**：原生图标到达之前，物品栏格子显示为空，不再回退到纸张代理。**已编译，尚未实机验证。**
5. **门的外观**：尚未复现。自测里新增了"先关门再选取"的步骤，但这一轮运行时用户也在同一个窗口里操作，自测的视角被干扰，选取仍然打在地面上。需要用户提供截图或描述。

这一轮碰撞（`dx=-0.2 passed=true`）、远端测试方块和第三方门的交互都通过。本轮出现过一次 Loom 缓存锁冲突：主端崩溃时后台的 Gradle 构建被中途打断，随后 VS Code Java 扩展的 Gradle 守护进程占用了 `mappings.jar`。用户关闭 VS Code 后，构建恢复正常。

## 第二轮用户反馈后的修改（2026-10-28 晚）

用户反馈：快速转头时远端的门被切掉一半，转回来后能看到它逐渐重新出现；云一直闪烁；远端门在物品栏里的材质和放置后的门不一样；希望主端等待另一端启动完成。

1. **主端等待**：后台 Runtime 首次有玩家实体时广播 `mmlf:world_ready`。主端在打开世界之前显示 `WaitingScreen`，收到后再进入世界，界面上有"直接进入（不等待）"按钮。session-5601058916960294529 实测：NeoForge 主端收到 `runtime_world_ready {"runtime":"fabric"}` 之后才打印 `SCENE READY runtime=neoforge`。
2. **转头时被切边**：远端帧通常比主端晚 30–40 ms（用户会话里最多 92 ms），快速转头时，新转进视野的区域后台还没有数据。改为后台渲染世界时把视野扩大到 1.25 倍（按正切缩放，`-Dmmlf.overscan` 可调），手部仍用原视野，合成时使用帧里记录的真实投影。代价是远端画面的像素密度降低约 20%，并且每一帧都要走重投影（实测每秒约 60 帧全部为重投影）。快速转头的效果还**需要用户实测**。
3. **云**：后台会话期间自动关闭云。实测后台帧里已没有云，也没有地面，覆盖率 6.3%，只剩远端拥有的方块。
4. **门的材质**：解出后台发来的 32×32 图标，与 Mod 自带的 `mcwdoors:item/oak_four_panel_door` 物品贴图一致；Macaw's Doors 的物品图标本来就和门方块的上下半贴图不同（原版门也是这样）。这是 Mod 本身的设计，不是传输错误。

本轮自测：相机控制、碰撞（`dx=-0.2 passed=true`）、远端 Fabric 测试方块和第三方门交互均通过。"先关门再选取"一步没有关上门（Fabric 侧只有一次开门记录），选取仍然打在地面上，所以远端门的选取和放置这一方向依然没有覆盖到。

5. **姿态预测**（用户反馈视野余量后仍有裁切感之后加入）：后台根据收到的主端姿态，平滑估计转头的角速度，相机朝向按"距最新姿态的时间 + 40 ms"外推（`-Dmmlf.poseLeadMs` 可调，外推最多 30°）。只预测相机，玩家朝向（准星射线、交互）仍用主端的真实朝向。合成使用帧里记录的实际渲染姿态，所以预测偏差只会减少余量，不会造成错位。**已编译，尚未实机验证**：快速转头属于主观体验，需要用户手动测试。

## 状态：快速转头裁切——未完成

用户确认：加入视野余量（1.25 倍）、后台姿态预测（25 ms）、后台 120 FPS 上限并关闭垂直同步之后，**超快速转动视角时，远端物体在屏幕边缘仍会被裁切，并能看到重新出现的过程**。该项标记为**未完成**。

实测原因：用户正常游玩时，后台实际只能跑到约 62 FPS（session-13619236781511829757，远端帧龄中位数 37.4 ms、p90 43.8 ms），因为笔记本 RTX 3060 要同时以 2560×1351 渲染两个客户端，GPU 已经饱和。主窗口几乎空闲时，后台能跑到约 105 FPS，帧龄约 15 ms（session-16176478497657835111）。

参考项目同样没有解决这个问题（只做重投影，预测默认关闭，并在文档中列为未解决）。可选的后续方向（均未实现）：

1. 降低后台渲染分辨率，换取帧率和更低的延迟；
2. 快速转头时，主端暂时显示远端已渲染的朝向；
3. 主端与远端逐帧同步（零裁切，但增加输入延迟）。
