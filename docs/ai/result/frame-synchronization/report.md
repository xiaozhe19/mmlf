# 帧同步与时钟校准（进行中）

## 实现

`FrameFile` 为三个映射槽分别使用独立锁文件中的非阻塞锁，读取和写入同一槽时互斥；所有槽忙时发布返回 -1，调用方不发送无效帧。保留奇偶序列及写入顺序屏障，拒绝奇数状态；增加帧格式标识及颜色、深度共同的 CRC32，复制后验证校验值，损坏帧不展示。CRC32 存在有限碰撞概率。该机制要求所有访问方合作且文件位于本机，锁只能证明互斥；进程崩溃时异常中断写入的持久化顺序和原子性仍待进一步验证。

世界帧元数据新增会话标识（token 的 SHA-256）、相机序列以及捕获时的时钟估计误差。主端拒绝会话不匹配、缺少相机序列、深度约定不兼容的帧。`FrameTiming` 基于 coordinator ping 的中点估计跨 JVM 时钟偏移，使用 RTT 的一半作为每端误差，并在判断帧龄时加上双方误差；未校准、过期校准、误差超过 100 ms、明显来自未来以及超过一秒安全上界的帧不显示。此误差界限依赖单调时钟在校准有效期内不明显漂移，未包括扫描输出和显示等待。

## 问题及处理

此前帧文件仅使用普通内存映射读写和 Java 内存屏障，缺少跨进程互斥证据；同一槽改用 OS 文件锁，冲突直接跳过。帧时钟原来直接使用最后一次偏移，既没有校准有效状态也不报告误差，可能错误估计帧龄；现在明确校准和不确定度，无法安全判断时拒绝显示。

## 测试

- `./gradlew.bat -PcoreOnly :common:test --tests dev.mmlf.common.FrameFileTest`：通过，包括竞争、奇数标记、独立写入 JVM 与读取 JVM 的帧完整性测试；后续新增子进程持锁写入奇数标记和损坏数据后 `Runtime.halt`，验证操作系统释放锁、损坏帧被拒绝且槽可复用。该场景不覆盖所有崩溃时间点。第一次运行因测试源码变量遮蔽 `java` 包导致编译错误，已修复后通过。
- `./gradlew.bat build`：通过，包括 `FrameTimingTest` 和既有测试，Fabric、NeoForge 构建成功；编译仍有既有 Mixin 映射警告。之后对 `FrameFile` 增加了发布顺序屏障，其后再次执行 `./gradlew.bat build`，包含 CRC 和发布顺序屏障的版本通过（37 个任务，17 个执行）。
- `./scripts/run-demo.ps1 -SelfTest -Foreground -LogLevel INFO`：会话 `runtime/session-15818930527184482130` 的 Fabric 主端和 NeoForge 后台进入世界并持续合成，脚本输出两次相机控制通过、碰撞通过，远端 use 返回 success=true；手动终止运行，进程退出码 1 不代表正常退出。该运行在增加 CRC 之前。随后会话 `runtime/session-14242447315903567397` 使用 CRC 版本启动并持续合成，脚本的相机控制和碰撞检查通过，远端交互记录 success=true；运行由本次测试手动终止。
