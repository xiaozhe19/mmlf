# 相机预测与指标（进行中）

## 实现

后台在相机设置开始记录时间，并在世界帧捕获时测量渲染耗时。主端按 Runtime 每秒通过控制事件反馈经过时钟校准的捕获到合成时间；后台使用指数平滑的渲染时间与反馈时间估算预测提前量，限制在 0–150 ms，五秒未获得反馈时恢复 `mmlf.poseLeadMs`（默认 25 ms）。角速度仍使用发布源的姿态时间差，角度反向、维度切换和长时间间隔的处理见实现。正常运行以最近最多 2048 个样本，每十秒输出帧龄、相机角度差和捕获耗时的 P50/P95/P99；这些不是重投影像素覆盖率。

## 问题和取舍

固定 25 ms 不随帧传输耗时变化；新模型由实际测量驱动，采用限幅和平滑避免瞬时异常直接主导预测。该模型尚未测量相机发布到后台首次读取的跨进程时间，以及屏幕显示等待，因此仍不是完整的显示时刻预测。角度差是实际源帧与主相机的差值，并非预先预测的误差。

## 结果

- `./gradlew.bat build`：包含预测模型与分位数单元测试的构建通过（37 个任务，19 个执行）；构建期间随后对 FrameFile 缓冲分配位置做了一项小修改，需最终重跑。
- `./scripts/run-demo.ps1 -SelfTest -Foreground -LogLevel INFO`：会话 `runtime/session-13192619437185242804` 中，Fabric 主端与 NeoForge 后台完成真实启动并持续合成，脚本记录相机控制和碰撞通过。日志示例：20:02:24，1196 个显示采样帧龄 P50 14.8621 ms、P95 19.27485 ms、P99 22.13495 ms，时钟误差估计 1.01475 ms；另一捕获窗口 1322 个样本的捕获 P50 7.5377 ms、P95 9.8173 ms、P99 10.7585 ms。这是一次运行的样本，不是改动前后对照，不能据此声称性能提升。
- 第二个后台 `fabric_extra` 在同会话启动，主端日志分别持续记录 `fabric_extra` 和 `neoforge` 的帧龄指标；例如 20:04:03–04 两个后台各约 800 个显示采样，P95 分别为 24.90 ms 和 24.26 ms。此结果证明两个帧流参与合成路径，但不单独证明画面内容、交互或深度关系正确。当前会话留给用户进行画面检查。

## 未完成

未形成 WebSocket 与共享内存的可比基准；姿态年龄、发布耗时、GPU 开销和覆盖率指标不完整。未进行快速反向、不同 Overscan、限帧压力及显示等待的系统化实验；尚不能证明预测减少边缘消失，也未确定问题根因。
